## The single most important correction

Part 4's kickoff proposed that the runaway is seeded because "the queued segment should
not contain the arm block at all", and called that the candidate fitting phase C's own
rule about boundaries.

**It is not a difference between the arms.** `sub_8284B9C0` writes the callback arm at
`r28 - 4` and then submits `[r28, armEnd + 4)` as the segment — the arm block is inside
its own segment *by construction* — and the PM4 control arm routes that segment into the
worker token queue on **5,696 of its 5,698 frames** without ever looping. Nothing about
the boundary is drawn in the wrong place.

Part 3's other candidate (duplicate ISR deliveries) is real and is an **effect**.

## What is actually happening

The hand-off is a **pipeline with gain one**, not a loop, and it is the same on
hardware, on the control arm and on the draw arm:

> a walk of a token buffer resubmits that frame's segments → the CP executes the arm
> blocks inside them → the ISR runs `sub_8284AAD0` → the worker is kicked with a token
> buffer pointer → it walks.

It converges on the control arm because the guest arms with a **new** token buffer every
frame, so the kicks generated by frame N drive frame N+1. It runs away on the draw arm
because the guest stalls: a whole 150 s boot produces **four** armings cycling between
**two** buffer pointers (`DC645600`, `DC68D500`), so each walk regenerates its own
wake-up on the same buffer.

Measured, same probe, both arms, one boot each, over the window in which `ringsub` is
verbose:

| | PM4 control | phase C draw |
|---|---|---|
| `[fence] arm cb=8284AAD0` | 768 | 12 |
| `[fence] isr cb=8284AAD0` | 766 | 856 |
| arm-carrying segments submitted to the ring | 853 | 1,149 |
| whole boot: `incr=1` submits / drains | 3,958 / 7,913 | 6 / 132,545 |

The control arm's whole-boot shape is the design working: **one `+1` per frame, exactly
two worker walks per frame, one decrement per pair**, and `dev+0x2B04` oscillating
0/1/2 forever.

**So the causal direction is:** the guest stalls → the pointer stops advancing → walks
outnumber submissions → `dev+0x2B04` goes negative → `sub_82846210`'s `!= 0` spin can
never exit → the guest stays stalled. Do not go looking for a seed inside the replay;
look for what stops the guest from advancing its token buffer.

## The brake we have never had, now built — and the one packet it names

On hardware the command processor **stalls** at the `WAIT_REG_MEM` packets the hand-off
block is built from. That stall is the only thing preventing the CP from getting ahead
of the CPU, and `gpu/pm4.cpp` has never had it:

```c
if (g_stopOnWait && depth == 0)   // <-- the whole of it
```

Every one of this title's hand-off waits is inside an `INDIRECT_BUFFER`, i.e. at depth
≥ 1, so `CZ_PM4_STOP_ON_WAIT` **could not fire on them in either of the two sessions
that measured and retired it**. Gotcha 151.

It now stalls at any depth. Because unwinding and retrying would re-walk the buffer from
the start — re-executing the arm and its `INTERRUPT`, which is the exact duplication the
stall exists to prevent — a stall records `(buffer va, dword)` per depth (`StallPlan` in
`gpu/pm4.cpp`), the `INDIRECT_BUFFER` handler propagates the stop up to the ring cursor,
and the next tick resumes at the recorded position. A deliberate stop is explicitly not
counted as a truncation.

**With it working, BOTH arms park at frame 1 on the same packet:**

```
[pm4] WAIT_REG_MEM #1 not satisfied, STOPPING: mem 1BF39466 value=00000001
      mask=FFFFFFFF ref=00000000 func=3
```

`1BF39466` is `mirror + 4` with the endian code `2` in its low two bits — i.e.
**SCRATCH_REG1, register `0x0579`, the one `sub_82841AD0` writes 1 to at the head of its
hand-off block** — and the wait holds until it reads back zero. Nothing in our runtime
ever writes that zero, on either arm, so the boot dies at `boot.bct` (file #5). The flag
stays off by default; it is now a working instrument rather than a dead one.

## Where to start, cheapest first

1. **Find the writer of `mirror+4` / register `0x0579`.** One run:
   `CZ_PM4_MEM_WATCH=BBF39464` on the **control** arm, which boots healthily — the same
   trick that named the counter's decrementer (gotcha 143). Two outcomes and they lead
   opposite ways:
   * a **packet** writes it → our `WAIT_REG_MEM` decode of that packet is wrong, because
     a wait satisfied only by a later packet in the same stream would deadlock hardware
     too. Check the poll address's low bits and the `info` field's function/mem bits
     against the emission in `sub_82845BA0` (disassembled at `82845BA0`–`82845D00`).
   * the **CPU** writes it → find the guest function and ask what condition reaches it
     (gotcha 107: the name says nothing about that).
2. **Only then** re-run `CZ_PM4_STOP_ON_WAIT=1` on both arms. With the brake able to
   engage, "does a CP that cannot run ahead stop the runaway?" becomes askable for the
   first time in this project.
3. **The fallback, if the brake cannot be made to work.** Every decrement comes from a
   walk of a stream whose segments were already submitted. `[fence] kick` flags
   `SAME-AS-PREVIOUS`, so the count of redundant walks is directly measurable; the
   question then is why the draw arm's guest fails to advance `[dev+0x3500]` between
   frames, which is a question about `sub_8284AB60` (it memcpys the `dev+0x3518` queue
   object over `dev+0x3500`, 0x18 bytes, at `8284ABA8`) and about `sub_82845290`, the
   queue **seal** that writes the `0xC0000000` sentinel at the tail.

## The instrument you inherit

`CZ_FENCE_PROBE=<N>` (`runtime/cpu/guest_probe.cpp`), one flag, on BOTH arms. New in
part 4:

```
[fence] submit  sub_82845AC0  now prints incr (r7, the counter delta) and queue (r8)
[fence] kick    sub_8284AAD0  NEW — the ISR callback that pushes a token buffer onto
                              the D3D worker's job ring: the buffer pointer, and
                              SAME-AS-PREVIOUS when it repeats
[fence] ringsub sub_828455C0  now prints EVERY entry of the first CZ_FENCE_RINGSUB
                              (default 4000) submissions, not two dwords of eight
```

`CZ_FENCE_RINGSUB=N` sets that budget. A replayed segment states its identity nowhere
else: this is what showed the control arm submitting each frame's arm-carrying segments
about twice and the draw arm submitting one of them **1,100 times**.

Set `CZ_FENCE_PROBE` high (400,000 is comfortable) — a saturated budget is a floor, not
a count (gotcha 109).

## The struct, unchanged and still proven rather than assumed

`obj = dev + 0x2AC4`, because `sub_82845AC0` locks `dev+0x2B08` and `sub_8284A960` locks
`obj+0x44`.

| field | address | meaning |
|---|---|---|
| `obj+0x10/0x14` | `dev+0x2AD4` | the interpreter's callback / user data (set by a `0x8C000000` token) |
| `obj+0x24` | `dev+0x2AE8` | the shared stream cursor |
| `obj+0x38` | `dev+0x2AFC` | one bit per CPU, `0x01000000 << cpu` |
| `obj+0x3C` | `dev+0x2B00` | interpreter nesting depth: `++` per queue pop, `--` per sentinel |
| `obj+0x40` | **`dev+0x2B04`** | **THE COUNTER** the engine spins on |
| `obj+0x44` | `dev+0x2B08` | the lock |
| `obj+0x48` | `dev+0x2B0C` | the tile RESUME cursor |
| `obj+0x164` | `dev+0x2C28` | the current bin mask |

Added in part 4, from the disassembly rather than from a run:

* **The token stream is a linked list of 0x10-byte records** written by `sub_82845AC0`:
  `[+4] = 0x81000000 | dwords`, `[+8] = segment GPU address`, `[+0xC] = 0xC0000000`
  (the sentinel). `sub_828453E8` then overwrites the PREVIOUS record's `+0xC` with the
  new record's address, so the walker's "a `0xCxxxxxxx` that is not exactly
  `0xC0000000` means jump to `value + 4`" case is the chain link. `sub_82845290` seals a
  queue by writing `0xC0000000` back at the tail.
* **`sub_82845DE0`'s fork on `dev+0x3460`**: nonzero appends the closed segment to the
  8-byte-record list at `[dev+0x350C]` (the async path — this is where the arm-A segment
  goes and why it is never submitted at its own close); zero emits a fence block and
  submits.
* **`sub_82845AC0`'s fork on `dev+0x2B04`**: zero builds a one-entry array on its stack
  and calls `sub_828455C0` directly; nonzero appends a token record and calls
  `sub_828453E8`. The `+= r7` happens on both paths.
* **`sub_8284B568`'s walk**: `0x8D000000` sets `[obj+0x168]`, `0x8C000000` sets the
  callback pair `[obj+0x10]/[obj+0x14]`, a top-bit-clear token is a sized block gated on
  `[obj+0x168] & [obj+0x164]`, and a `0x8xxxxxxx` token is a **rendezvous**: `[obj+0x64]`
  counts arrivals and only the walker that makes it equal `[obj+0x3C]` calls
  `sub_8284B228` (which is what actually submits). That is why one frame's segments are
  submitted once even though two tile walks reach them.
